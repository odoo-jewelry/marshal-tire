## Context

`purchase_price_control` вычисляет `purchase.order.line.planned_sale_price` из `effective_purchase_price` и сохраняемого снимка `current_markup`. Поле сейчас только вычисляемое и недоступно для редактирования. Действия `Update` и `Update All` используют результат этого расчёта для записи `product.lst_price`.

Стандартный Odoo 19 поддерживает редактируемые вычисляемые поля через `compute` вместе с `inverse`; такой подход уже используется в моделях Purchase. Для точного независимого ручного значения требуется явно хранить его и признак переопределения.

## Goals / Non-Goals

**Goals:**

- разрешить прямой ввод `planned_sale_price` для инициализированной товарной строки;
- сохранять ручную цену точно, не изменяя `current_markup` и другие расчёты;
- не перезаписывать ручную цену при изменении базы;
- возвращать автоматический расчёт только через `Fill Current Prices`;
- не изменять товар до явного `Update` или `Update All`;
- обеспечить одинаковое поведение через форму, ORM и внешние вызовы.

**Non-Goals:**

- история ручных вводов;
- изменение правил округления, согласования заказов, складской оценки или прав доступа;
- ручной ввод для секций, заметок, авансовых и неинициализированных строк.

## Decisions

### Редактируемое вычисляемое поле с явным переопределением

`planned_sale_price` остаётся вычисляемым полем и получает стандартный обратный метод. Два технических сохраняемых поля строки хранят точное ручное значение и признак его наличия. В форме поле становится редактируемым только для подходящих строк с `price_snapshot_initialized=True`.

При записи ручной цены обратный метод:

1. проверяет пригодность строки и наличие снимка;
2. сохраняет введённое значение без округления;
3. включает признак ручного переопределения, не записывая `current_markup`.

Пока признак установлен, compute возвращает сохранённое ручное значение и не применяет к нему округление. Изменение зависимостей `effective_purchase_price` продолжает пересчитывать закупочные показатели, но не плановую продажную цену. `Fill Current Prices` очищает ручное значение и признак, после чего используется прежняя формула и округление вверх. Обновление товара через `Update` сохраняет ручную цену и не сбрасывает переопределение; пользователь может явно сбросить его последующим `Fill Current Prices`.

Проверка пригодности и инициализации выполняется на уровне модели, а не только интерфейса.

### Сохранение товара остаётся явным

Редактирование `planned_sale_price` меняет только техническое ручное значение строки. Запись `last_purchase_price`, `lst_price` и, для Standard Price, `standard_price` по-прежнему выполняется только существующими действиями. Переходы состояний, отмена, повторное подтверждение, блокировка и копирование заказа не получают новых побочных эффектов.

### Область изменений

- `main/purchase_price_control/models/purchase_order.py`: явный сброс переопределения при заполнении текущих цен;
- `main/purchase_price_control/models/purchase_order_line.py`: хранение переопределения, inverse и проверка данных;
- `main/purchase_price_control/views/purchase_order_views.xml`: доступность редактирования;
- `main/purchase_price_control/tests/test_purchase_price_control.py`: сценарии прямого ввода, округления, пересчёта, проверки базы и отсутствия записи товара;
- переводы модуля — только если появляется новый пользовательский текст ошибки.

Новые модели, ACL, record rules, XML-данные и зависимости не нужны. Добавление двух nullable/default технических колонок выполняется обычным обновлением модуля; отдельная миграция данных не требуется, существующие строки начинают без ручного переопределения.

### Права, компании и пакетная обработка

Обратный метод работает с полным recordset. Запись технического переопределения требует обычных прав на строку заказа; повышение прав не применяется. При ошибке любой строки стандартная транзакция Odoo откатывает весь вызов. Межфирменные цены и настройки округления не смешиваются.

### Проверка

Серверные тесты должны покрыть точное сохранение `12` без превращения в `12.01`, неизменность наценки, сохранение ручной цены после изменения базы, сброс через `Fill Current Prices`, неинициализированную строку, отсутствие неявной записи товара и сохранение прежнего автоматического сценария. Дополнительно требуются проверка синтаксиса, компиляция XML, обновление модуля и сфокусированный набор тестов `purchase_price_control`. Браузерная автоматизация не выполняется согласно правилам проекта.

### Отклонённые варианты

- Реализация только через `onchange` отклонена: импорт, ORM и внешние вызовы получили бы другое поведение.
- Изменение `current_sale_price` отклонено: это снимок фактической цены товара, а не план пользователя.
- Обратный расчёт `current_markup` отклонён: ручная продажная цена не должна менять другие показатели.

## Risks / Trade-offs

- В ручном режиме `planned_sale_price` намеренно может не соответствовать произведению эффективной закупочной цены и наценки.
- Добавляются две технические колонки, но их значения по умолчанию сохраняют прежнее поведение установленных баз.
