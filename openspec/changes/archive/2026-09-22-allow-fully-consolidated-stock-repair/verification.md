# Проверка реализации

Дата: 2026-09-17. Реализованы все задачи изменения. Канонические спецификации синхронизированы, документация пересобрана и изменение архивировано 2026-09-22.

## Результат

- Полностью перенесённая история допускается к обычному исправлению нулевой оценки. Неполный перенос и архивная поглощённая карточка сохраняют понятную причину отказа; сообщение для поглощённой карточки содержит имя основной.
- Проверяются состав и версии источников. Для основной карточки используется `cost_recompute_revision`, для архивных источников — `consolidation_revision`; создание самого просмотра не вызывает ложного устаревания.
- Пропущенная складская деталь позволяет открыть отдельный исторический пересчёт одного товара с сохранением компании и серверной проверкой прав. Исходная операция и её выборка не меняются.
- Добавлены переводы и кнопки в существующее представление. Обязательные зависимости базового модуля, модели, ACL и бухгалтерские правила не расширены.

## Автоматизированные проверки

Все команды Odoo использовали `/etc/odoo/odoo.conf` и явную базу. Временные процессы использовали порты 8077 и 8078, постоянный сервер — 8069.

1. Полный серверный прогон `--test-tags /pos_cost_recompute,/pos_historical_stock_writeoff` на `odoo_tire_testing`: **157 тестов, 0 ошибок и 0 отказов**. Журнал: `/tmp/consolidated-repair-verified.log`.
2. Дополнительный тест `TestConsolidatedHistory.test_ordinary_repair_does_not_require_history_permission`: **1 тест, 0 ошибок и 0 отказов**. Подтверждён обычный просмотр и применение пользователем с правами POS/склада без права исторического пересчёта. Журнал: `/tmp/consolidated-repair-permission.log`.
3. Созданная этой работой временная база пересоздана после успешного полного прогона; установлен только `pos_cost_recompute` и его штатные зависимости. `product_card_consolidation` и `pos_historical_stock_writeoff` остались в состоянии `uninstalled`. **3 теста, 0 ошибок и 0 отказов**: обычная себестоимость, исправление по поступлению, исключение некорректных источников. Журнал: `/tmp/consolidated-repair-standalone.log`.
4. Независимые курсоры PostgreSQL подтвердили отказ при невидимой текущему снимку вставке движения или изменении остатка архивного источника, а также блокировку записи после захвата источников исправлением. Эти сценарии входят в полный прогон.
5. Проверены синтаксис Python, XML, русские каталоги переводов, отсутствие пробельных ошибок и строгая валидация OpenSpec.

При первом прогоне новых тестов выявлены ошибки их подготовки: обязательность предварительного просмотра объединения, отдельные права на объединение и повторяющийся UUID чека. Подготовка исправлена, итоговые прогоны выше прошли полностью. Производственные ограничения для обхода этих ошибок не ослаблялись.

## Обновление базы разработки

На `odoo_tire` выполнено:

```text
odoo --http-port=8078 -c /etc/odoo/odoo.conf -d odoo_tire -u pos_cost_recompute,pos_historical_stock_writeoff --stop-after-init
```

Версии после обновления: `pos_cost_recompute` — `19.0.1.1.5`, `pos_historical_stock_writeoff` — `19.0.2.0.1`. Журнал: `/tmp/consolidated-repair-development-update.log`.

До обновления сохранены количество записей и отпечатки значимых полей шести таблиц. После обновления совпали движения, остатки, операции пересчёта, складские детали и журнал объединений. Общее сравнение строк POS сначала отличалось из-за двух записей, созданных после исходного снимка; ограничение сравнения прежними строками подтвердило совпадение их количества, товаров, количеств, себестоимости и признаков завершённости. Ни одна операция переоценки хозяйственных данных в этой базе не запускалась.

Постоянный процесс Odoo перезагружен штатным `SIGHUP`; вход `/web/login?db=odoo_tire` на порту 8069 вернул HTTP 200.

## Ограничения проверки

- Браузерные автоматические тесты не запускались согласно правилам проекта. Ручная визуальная проверка кнопки в браузере не выполнялась; подтверждены компиляция представления и серверное действие.
- Конкретная пользовательская переоценка не применялась: пользователь должен обновить предварительный просмотр и проверить предлагаемые суммы.
- Канонические спецификации `pos-cost-recompute` и `pos-zero-stock-valuation-repair` синхронизированы и успешно проверены OpenSpec; существующие карточки функций сохранены без изменений. Их описания ограничений требуют ручного пересмотра. Документация пересобрана; новых отличий в клиентских страницах этого изменения генератор не создал.
