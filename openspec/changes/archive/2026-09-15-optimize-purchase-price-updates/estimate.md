# Оценка реализации

## Итог

- Всего сценариев: 13.
- Implementation-driving сценариев (задают изменение): 3.
- Verification-only сценариев (проверяют общий механизм или прежнее поведение): 10.
- Implementation clusters (группы реализации): 2.
- Implementation units (условные единицы): 5.
- Fast path: нет; затронуты пропуск записи цен, права и стандартные последствия стоимости.
- Эмпирический размер: medium.
- Производительность: предварительный ориентир 1 час на единицу, без калибровки по истории проекта.
- Базовая оценка: 5 часов, включая обычную проверку.
- Исключительные дополнительные работы: 1–2 часа на сравнительные замеры четырёх режимов обработки 266 строк.
- Итоговая оценка: **6–7 часов** активной работы разработчика Odoo среднего уровня.
- Уверенность: средняя; точки расширения известны, но выигрыш полного пользовательского запроса не установлен.

Обычные тесты, проверка синтаксиса и одно обновление модуля входят в эти группы. Проверочные сценарии не получают отдельные единицы. Повторное применение одного принципа сравнения не считается отдельной архитектурой; версия модуля и файлы не образуют отдельные группы.

## Проверка структуры спецификаций

### Сценарии, которые следует разделить

Нет: перечисление стадий жизненного цикла проверяет одно требование отсутствия новых побочных действий. Сброс ручной цены, инициализация, повторный вызов и ошибки доступа выделены отдельно.

### Дублирующиеся или пересекающиеся сценарии

Нет лишнего дублирования в delta. Повтор и откат уточняют прежние гарантии для смешанных изменившихся и пропускаемых записей. Общие сценарии не образуют отдельной реализации.

### Недостающие сценарии

Нет в согласованном объёме. FIFO/AVCO, Standard Price, компании, копирование и состояния уже покрыты канонической спецификацией и существующими тестами; их повторный прогон включён в задачи. Границы точности, общие варианты и несколько компаний дополнительно перечислены в технической проверке.

### Недостаточно определённые или противоречивые сценарии

Абсолютный норматив времени не заявлен: обязательный результат — сокращение лишних записей и сохранение значений. Полная задержка интерфейса требует отдельного измерения. Устаревшая каноническая карточка отмечена в design.md и не меняет этот объём.

## Расчёт трудозатрат

- Сумма единиц: 2 + 3 = 5.
- Производительность: 1 час на единицу.
- Базовые часы: 5; ориентировочно 3 часа на код и 2 часа на профильные тесты, статические проверки и обновление модуля. Это распределение внутри оценки, не дополнительная сумма.
- Дополнительное архитектурное исследование: 0 часов.
- Миграция и обработка данных: 0 часов.
- Сравнительные массовые замеры: 1–2 часа на подготовку сопоставимых данных и четыре режима по пять повторов до/после, с отчётом SQL/ORM/времени.
- Другие исключительные работы: 0 часов.
- Итог: 6–7 часов; коэффициенты за домен, количество файлов и применение ИИ не используются.

Схема одновременно требует отделять проверку при расчёте и включает обычную проверку в единицы; выше она показана отдельной составляющей без двойного начисления. CLI сообщает об ошибочном типе одного элемента `rules.estimate` в существующем config.yaml; правила прочитаны вручную, схема оценки применена полностью, конфигурация не менялась.

## Стратегия проверки

### Автоматизированные тесты

Обязательны: известная регрессия лишних записей и риск обхода доступа при оптимизации. Использовать существующий TransactionCase. Проверить 13 сценариев, счётчики записи бизнес-полей, точность, общую цену вариантов A → B → A, компании и стандартные последствия стоимости. Не проверять производительность нестабильным порогом времени в тесте.

### Module update и smoke verification

Проверить синтаксис/импорты, обновление `purchase_price_control` и профильные тесты на разрешённой тестовой базе. Сравнить цены и снимки до/после обновления. Новые XML, права и зависимости не требуются. Браузерные тесты запрещены; поведение браузера и сети автоматически не проверяется.

## Основные факторы сложности

Точность разных полей, сохранение полного сброса ручной цены, общая цена шаблона с доплатами вариантов и штатные права при пропущенной записи. Существующие расчёты, порядок кандидатов и тестовая база повторно используются.

## Риски

| Risk flag | Влияние | Как проверяется или снижается |
|---|---|---|
| bulk | Порядок общих цен и производительность больших заказов | Последовательное сравнение, A → B → A, четыре сравнительных режима |
| security | Пропуск встроенных проверок записи | Штатные проверки модели, записей и полей, включая общую цену шаблона |
| accounting | Лишняя или пропущенная запись реальной стоимости | Обычный ORM для изменения, тесты истории и партий |
| stock | Случайное изменение FIFO/AVCO или жизненного цикла | Существующие регрессионные тесты |
| uncertainty | Серверное ускорение может не устранить задержку интерфейса | Не обещать результат вне измеренного участка |

## Предположения

- Объём ограничен тремя явными действиями `purchase_price_control`.
- Тестовая база и установленные зависимости доступны; новые компоненты не устанавливаются.
- Существующие пользовательские изменения сохраняются, конфликтующего изменения этих методов нет.

## Исключено из оценки

Исправление рабочих цен, округление, себестоимость FIFO, приёмка, миграции, браузер/сеть, новые фоновые задания и переработка канонической карточки функции.

## Требуется discovery

Нет для указанной оптимизации: проектные и стандартные пути изучены. Сравнительные замеры — конкретная проверка, уже включённая отдельно.

## Условия пересмотра оценки

Новые ограничения записи в других расширениях, недоступность тестовой среды, необходимость изменять контракт общих цен либо подтверждённая задержка вне трёх действий потребуют пересмотра объёма и оценки.

## Фактический результат

Реализация проверена на P00127 с 266 строками. Каждый режим выполнен пять раз с откатом транзакции, одинаковым пользователем и сбросом кеша между повторами. Указана медиана без профилировщика; браузер и сеть не измерялись.

| Режим | До: время / SQL / записи строк / записи товаров | После: время / SQL / записи строк / записи товаров | Результат |
|---|---|---|---|
| Одна изменённая цена | 0,0510 с / 18 / 266 / 1 | 0,0282 с / 15 / 1 / 1 | Время −45%; устранены 265 записей снимков |
| Все 266 цен реально изменены | 0,5729 с / 548 / 266 / 266 | 0,3562 с / 283 / 266 / 266 | Время −38%; SQL −48% при том же числе необходимых записей |
| Повторный Fill | 0,0470 с / 11 / 266 / 0 | 0,0246 с / 8 / 1 / 0 | Время −48%; записана только строка с существующей ручной ценой |
| Устаревшие снимки, товары уже актуальны | 0,6151 с / 548 / 266 / 266 | 0,1024 с / 9 / 266 / 0 | Время −83%; устранены 266 лишних записей товаров |

В P00127 повторный Fill корректно записывает одну строку: у «Латки №5» сохранялось ручное переопределение New Sale, которое Fill обязан сбросить. Автоматизированный тест без ручного переопределения подтверждает ноль записей.

Проверка реализации:

- обновление `purchase_price_control` на `odoo_tire_testing` успешно;
- 34 профильных тестовых метода выполнены без ошибок, включая все 13 сценариев delta-спецификации и существующие регрессии;
- контрольный заказ, строка и товар сохранили цены, снимок, ручную New Sale, сумму, состояние и `write_date` после обновления модуля;
- временные контрольные записи из тестовой базы удалены после проверки;
- синтаксис и импорты Python, manifest, XML, `git diff --check` и строгая проверка OpenSpec прошли;
- браузерные тесты не выполнялись по правилам проекта; задержка браузера и сети остаётся неизмеренной.

- Фактические часы разработчика: не применимо; реализация выполнена агентом, активное машинное время отдельно не тарифицировалось.
- Отклонение от оценки: человеческая оценка 6–7 часов не калибруется по машинному выполнению.
- Причина отклонения: сопоставимых исторических данных по ручной реализации нет.
- Фактические часы на unit: не рассчитываются.
- Изменения для будущей калибровки: накапливать отдельно человеческие трудозатраты и машинное время; текущие замеры пригодны для калибровки производительности функции, но не разработки.
