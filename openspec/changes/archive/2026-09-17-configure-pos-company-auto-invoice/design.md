## Context

Проверена установленная Odoo 19 Community и проектные расширения:

- `point_of_sale/static/src/app/models/pos_order.js`: `PosOrder.setPartner()` проверяет возможность редактирования, назначает клиента, вызывает `updatePricelistAndFiscalPosition()` и без настройки включает `to_invoice` для `partner.is_company`.
- `point_of_sale/static/src/app/screens/payment_screen/payment_screen.js`: ручная отметка использует `setToInvoice()`; при возврате продажи со счётом стандартный экран сам включает выставление счёта. Эти правила нельзя подавлять глобальным запретом `setToInvoice(true)`.
- `point_of_sale/models/pos_config.py` и `pos_load_mixin.py`: конфигурация загружается стандартным механизмом; пустой список `_load_pos_data_fields()` означает чтение всех полей. Нельзя заменить его списком из одного нового поля.
- `point_of_sale/views/res_config_settings_views.xml`: настройки выбирают конкретную кассу через `pos_config_id`, рядом есть блок `pos_default_journals`.
- `main/tire`: уже содержит небольшие расширения моделей и интерфейса кассы; `tests/test_pos_product_short_name.py` проверяет стандартную загрузку дополнительных данных в POS.
- `main/pos_order_correction`: счёт запрещает исправление чека независимо от открытой смены. Новая настройка не изменяет это ограничение.

Изменение является предпочтением интерфейса, а не запретом выставлять счета клиентам-компаниям. Новых денежных операций или параллельного источника бухгалтерских данных не требуется. Критического конфликта со стандартным жизненным циклом нет при сохранении ручного выбора и правил возврата.

## Goals / Non-Goals

**Goals:**

- Настройка отдельно для каждой кассы с исходным значением `False`.
- Сохранение текущего выбора счёта при выключенной автоматике.
- Возврат стандартного поведения при включённой настройке.
- Безопасное обновление существующей базы без изменения заказов и счетов.

**Non-Goals:**

- Удаление, отмена или исправление уже выставленных счетов, в том числе обсуждавшегося чека.
- Изменение механизма долгов, закрытия смены, платежей, возвратов и складских операций.
- Немедленная рассылка изменения настройки во все открытые кассовые вкладки.
- Общий запрет счетов, новая роль доступа или отдельный модуль только ради этой настройки.

## Decisions

### 1. Размещение и источник значения

Расширить существующий `main/tire`:

| Файл | Изменение при реализации |
| --- | --- |
| `models/pos_config.py` | Новое поле `auto_invoice_company_customer`, `fields.Boolean(default=False)` на `pos.config` |
| `models/res_config_settings.py` | Редактируемое связанное поле `pos_auto_invoice_company_customer` через `pos_config_id` |
| `models/__init__.py` | Подключение расширений |
| `views/res_config_settings_views.xml` | Наследование `point_of_sale.res_config_settings_view_form`, отдельная настройка рядом с `pos_default_journals` |
| `static/src/app/models/pos_order.js` | Небольшое расширение выбора клиента |
| `__manifest__.py` | Представление, ресурс в `point_of_sale._assets_pos`, повышение версии |
| `i18n/ru.po`, `i18n/uk.po` | Перевод подписи и пояснения |
| `tests/test_pos_company_auto_invoice.py`, `tests/__init__.py` | Серверные проверки конфигурации и передачи данных |

Единственный источник настройки — поле `pos.config`; не использовать глобальный параметр `ir.config_parameter` или поле компании. Источник выбора для конкретного заказа — стандартное `to_invoice`; отдельных признаков «выбрано вручную» не нужно.

Исходная строка интерфейса: `Automatically enable invoicing for company customers`. Русская подпись: «Автоматически включать счёт при выборе клиента-компании». Пояснение сообщает, что при выключенной настройке счёт можно выбрать вручную и после сохранения следует перезагрузить кассовый интерфейс.

При реализации обнаружен локальный `main/tire/i18n/tire.pot`, исключённый из Git общим правилом `*.pot`. Стандартный загрузчик Odoo использует его для сопоставления строк и отбрасывает отсутствующие в нём новые переводы. В локальный шаблон добавлены только новые строки этой настройки; существующие строки сохранены. Если при внедрении присутствует такой шаблон, его необходимо актуализировать вместе с PO-файлами. Изменение правил Git и принудительное добавление генерируемого шаблона не требуется.

### 2. Передача конфигурации в кассу

Использовать стандартное чтение конфигурации. В установленной реализации новые поля уже включаются при чтении всех полей: дополнительное переопределение загрузчика не требуется. Серверный тест должен проверять фактический результат `_load_pos_data_read()`, а не предполагать наличие поля по его объявлению.

Две кассы, включая кассы одной компании, получают свои значения. Обновление интерфейса после сохранения настроек — граница применения нового значения; открытые документы при загрузке не пересчитываются.

### 3. Узкое расширение выбора клиента

Использовать стандартный `patch(PosOrder.prototype, ...)` только для `setPartner()`, поскольку отдельного расширяемого правила автоматического включения в Odoo 19 нет.

Перед стандартным вызовом сохранить значение `to_invoice`, вызвать `super.setPartner(...)` с исходными аргументами и сохранить его результат. Если клиент является компанией, настройка выключена и стандартный выбор включил ранее выключенный флаг, восстановить прежнее значение через `setToInvoice(false)`. Возвратить стандартный результат. Не подавлять ошибки стандартного вызова; восстановление выполнять только после успешного выбора.

Этот подход сохраняет стандартные проверки редактируемости, назначение клиента, прайс-лист и налоговую позицию. В текущем стандартном методе переключение флага не создаёт счёт; документ создаётся позже при подтверждении продажи. Повторный выбор компании снова следует настройке. Ранее включённая отметка, независимо от её происхождения, сохраняется: никакой новый механизм определения намерения кассира не вводится.

Не переопределять глобально `setToInvoice()`, оплату заказа, серверное выставление счёта или обработку возврата. Физическое лицо проходит стандартный метод без дополнительного изменения флага. Правило оплаты возврата со счётом сохраняется.

### 4. Жизненный цикл и границы

- Подтверждение заказа и повторная синхронизация используют стандартный флаг и стандартную обработку; новая настройка не создаёт документов самостоятельно.
- Отмена выбора клиента, отказ от продажи и отмена заказа не получают новых действий.
- Открытие существующего заказа и перезагрузка кассы не должны менять его сохранённый флаг; правило применяется только при новом выборе клиента.
- Копирование конфигурации сохраняет её настройку по обычным правилам копирования полей; значение по умолчанию относится к новой конфигурации без явно заданного значения.
- Копирование заказа, импорт и прямые серверные запросы сохраняют стандартное поведение. Не сбрасывать явно переданное `to_invoice` на сервере: настройка управляет удобством выбора в кассе, а не бизнес-запретом.
- Платёж на «Аккаунт клиента» без счёта сохраняет существующий механизм долга и доступность исправления при выполнении его прежних условий.

### 5. Доступ и несколько компаний

Новых моделей, групп, записей ACL и правил доступа нет. Расширения `pos.config` и `res.config.settings` используют их существующие права. Настройка отображается в стандартной секции настроек кассы; запрещено расширять доступ кассира ради сохранения настройки. Загрузка POS должна сохранять обычные ограничения на чтение конфигурации. Прямую запись без нужных прав и доступ к кассе другой компании проверить с обычными пользователями.

### 6. Обновление базы

Добавление поля со значением `False` стандартным обновлением модуля должно инициализировать новую колонку существующих касс. Не использовать постоянно выполняемый сброс значений, XML-записи поверх касс или очистку документов. Повторное обновление должно сохранять установленное `True`. Отдельная миграция не планируется: достаточность стандартной инициализации подтвердить проверкой обновления с существующей конфигурацией.

Обновление `tire` выполнять с явными `-c /etc/odoo/odoo.conf`, `-d` и свободным временным портом от `8077`, сохраняя фактический `addons_path`. При внедрении перезагрузить ресурсы открытых касс. Удаление поля/расширения возвращает стандартный автоматический выбор для дальнейших операций, но не переписывает документы.

### 7. Проверка

- Серверные тесты: исходное значение, сохранение через настройки, две независимые кассы и данные стандартной загрузки POS; существующие права и компании с представителями ролей.
- Проверка обновления: существующая касса получает `False`, повторное обновление сохраняет `True`; заказы со счетами и черновики с обеими отметками не изменены.
- Проверки Python, XML, переводов и доступных средств синтаксической проверки JavaScript; компиляция наследуемого представления при обновлении.
- Ручная матрица кассы: автоматика выключена/включена, компания/физическое лицо, исходный флаг выключен/включён, повторный выбор компании, ручное снятие и установка, прайс-лист и налоги, возврат продажи со счётом, перезагрузка настроек.
- Проверить подтверждение обычной продажи с ручным счётом и без него, а также стандартную серверную обработку явно переданного флага. Существующие серверные средства тестирования Odoo использовать без браузера; не считать их проверкой выполнения JavaScript.
- Не создавать и не запускать HOOT, браузерные QUnit, туры или иные автоматические проверки в браузере. Не устанавливать инструменты и зависимости. Если ручной доступ к интерфейсу недоступен, явно оставить поведение браузера непроверенным.

### 8. Отклонённые варианты

- Постоянно выключить автоматическое включение: не даёт запрошенного выбора кассам.
- Глобальная настройка компании: смешивает предпочтения разных касс.
- Копировать стандартный `setPartner()` целиком: дублирует обработку клиента, цен и налогов.
- Всегда сбрасывать `to_invoice` при выключенной опции: теряет ручной выбор и может нарушить возвраты.
- Удалить счета или разрешить исправление счетов через существующий модуль: выходит за объём и затрагивает бухгалтерскую согласованность.
- Поместить настройку в `pos_order_correction`: автоматическое выставление счёта относится к обычному оформлению продажи, а не к исправлению истории.

## Risks / Trade-offs

- **accounting:** влияние косвенное, через намерение выставить счёт; стандартное создание и проводки не меняются. Нужна проверка ручного счёта и возврата.
- **migration:** исходное значение существующих касс намеренно меняет дальнейший выбор клиента; документы сохраняются. Повторное обновление не должно сбрасывать настройку.
- **view-conflict:** небольшое наследование стандартной формы может конфликтовать с другими представлениями; проверить компиляцию в целевой базе.
- **uncertainty:** стандартный `setPartner()` может измениться при обновлении Odoo; при таком обновлении повторно проверить узкое расширение. Другие расширения этого метода не должны терять свои побочные эффекты.
- Автоматически проверяется серверная часть; JavaScript и взаимодействие кассира требуют ручной проверки в рамках запрета браузерных тестов.
