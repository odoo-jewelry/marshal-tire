# Проверка реализации

## Сценарии спецификации

| Сценарии | Проверка |
| --- | --- |
| I01–I03 | Серверные тесты недостачи по двум ценам FIFO, штатного `stock.scrap` и неподтверждённого источника. На клиентской копии для пасты из P00001 изолированный расчёт дал 725 → 870 для поступления и списания, остаток 0. |
| I04–I08 | Серверные тесты полного остатка из выбранного и невыбранного поступления, будущего поступления, цепочки излишек → недостача → излишек, нулевого и отрицательного остатка. Проверены остатки и стоимость карточки. |
| I09 | Отказ при недоступном более раннем основании проверен с подменой результата `_get_last_in()`; цена текущей карточки не используется, изменения откатываются. В естественной допустимой истории с выбранным положительным поступлением отсутствие всех предшествующих приходов недостижимо. |
| I10–I13 | Проверены ранние излишек/недостача/списание, смешанные направления, совпадение излишка с поступлением и несколько излишков в одну секунду. |
| I14–I15 | Проверены стоимость POS-продажи и возврата после излишка, неизменность выручки и исключение связанного с POS списания из проданных количеств. |
| I16–I19 | Проверены ручная оценка каждого типа корректировки, ограничение доступа к `stock.scrap`, запрет ложного `is_inventory`, изоляция компаний при положительном, нулевом и отрицательном остатке. На клиентской копии защищённый перенос объединённой щётки отдельно отклонён. |
| I20–I21 | Поздний отказ после записи излишка полностью откатывает закупку и оценки. Проверки с двумя курсорами охватывают добавление корректировки и проведение/изменение `stock.scrap` одновременно с пересчётом. |
| I22–I24 | Снимки физических фактов и документов до/после, пустой повтор исправления, открытие и отмена мастера без деловых изменений. |
| I25–I27 | Обновление модуля не меняет клиентские цены, движения, списания, остатки и стоимость POS. Проверены текст мастера и точные непересекающиеся счётчики: 1 поступление, 2 излишка, 3 недостачи, 4 списания, 7 расходов. |

## Клиентская копия и границы приёмки

- Изолированный расчёт пасты P00001: `stock.move` поступления 1235 и списания 1611 изменились бы с 725 на 870; физический остаток остался 0. Пробная транзакция отменена.
- Изолированный расчёт обычного излишка 1632: стоимость изменилась бы с 53,04 на 63,65 по историческому остатку из 4 единиц; пробная транзакция отменена. Излишек 1635 остался 9,00 по собственному составу исторических поступлений.
- Полная выборка P00001–P00005 отклоняется атомарно из-за неподдерживаемого товара с партиями/настройками оценки ещё до проверки переноса. Отдельная проверка товара щётки подтвердила самостоятельный отказ: история объединения не доказана полностью. Успех изолированных примеров не означает успех всего набора.
- После обновления копия и основная база совпали для 308 строк закупок, 472 складских движений, 14 списаний, 642 остатков и 125 строк POS по товарам указанных заказов. Основная база использовалась только для чтения.

## Проверки и ограничения окружения

- Синтаксис Python и XML, `msgfmt --check --check-format`, `openspec validate --strict`, обновление `purchase_cost_recompute` и сфокусированные тесты прошли. На чистой базе без `pos_historical_stock_writeoff` и `product_card_consolidation` установка и 35 направленных тестов прошли; затем полный набор модуля завершился без ошибок: 103 теста, из которых два ожидаемо пропущены из-за отсутствия необязательных модулей. На клиентской копии проверка модуля с исключением одного теста объединения, блокируемого открытой POS-сессией, завершилась без ошибок: 100 тестов.
- Дополнительный набор `TestPurchaseCostIntegration` модуля `pos_historical_stock_writeoff`: одна проверка прошла, 10 остановились на штатном запрете Odoo архивировать товар при уже открытой POS-сессии в копии клиентской базы. Продуктовые данные и состояние клиентских сессий для обхода этого ограничения не менялись.
- Автоматические браузерные проверки не запускались по правилам проекта. Фактическое выполнение полной выборки клиента остаётся недоступным до отдельного решения ограничений товара и объединения.
- База `odoo_tire_testing` отсутствовала до задачи, создавалась только для проверок и удалена после них. Основная `odoo_tire` сохранена. Существовавшее до задачи файловое хранилище с именем тестовой базы не удалялось.
