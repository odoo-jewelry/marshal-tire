Итоговая оценка — реалистичное активное рабочее время мидл Odoo-разработчика
от начала анализа до готового и обычно проверенного изменения. Обычные focused
tests, static checks, один module update и обычный non-browser smoke входят в
cluster и не прибавляются повторно.

## Покрытие сценариев

| Спецификация | Scenario | Классификация | Cluster | Risk flags | Обоснование |
|---|---|---|---|---|---|
| | | implementation-driving / verification-only | | | |

Классификация:

- `implementation-driving` — требует нового или изменённого production-поведения;
- `verification-only` — не требует отдельной реализации и проверяет общий
  механизм, стандартное поведение или отсутствие регрессии.

Каждый Scenario должен присутствовать в таблице ровно один раз.

## Implementation clusters

| Cluster | Механизм реализации | Покрываемые сценарии | Units | Обоснование |
|---|---|---|---:|---|
| | | | | |

Использовать только значения:

| Units | Значение |
|---:|---|
| 0 | Только проверка; независимое production-изменение отсутствует |
| 0.25 | Очень маленькое декларативное изменение: простой filter, domain, label, attribute или известная XML-вставка |
| 0.5 | Небольшое изменение одного view/configuration record либо повтор уже установленного паттерна |
| 1 | Законченное локальное изменение одной модели, view или известного extension point вместе с обычной проверкой |
| 2 | Согласованное поведение связанных записей внутри одной подсистемы |
| 3 | Нетривиальная кастомная логика или стандартный handoff между подсистемами с focused validation |
| 5 | Существенная lifecycle-координация, cancellation/retry или несколько взаимодействующих записей |
| 8 | Сложная логика Stock, Procurement, MRP, Accounting, миграции, bulk, external integration или failure recovery |
| 13 | Крупная неделимая архитектурная неопределённость; требуется split или discovery |

Правила:

- Оценивать общий механизм реализации, а не каждый Scenario отдельно.
- Не считать один и тот же code/XML/configuration mechanism несколько раз.
- Для повторов одного паттерна учитывать только добавочную стоимость.
- Standard Odoo, существующий проектный код и legacy должны уменьшать Units,
  если реально сокращают реализацию.
- Не считать отдельными clusters изменение версии модуля, manifest, файлы,
  тесты или описание регрессии.
- Не применять дополнительный коэффициент за количество addons, моделей,
  файлов или затронутых доменов.
- Несколько hooks одной модели, реализующих одно небольшое связное поведение,
  обычно образуют один cluster, а не несколько.
- Cluster включает focused investigation, production change, обязательные
  focused tests, обычные static checks, один module update и обычный smoke.

## Расчёт трудозатрат

До накопления собственной статистики использовать ориентир:

```text
1 implementation unit = 1 час мидла
```

Расчёт:

- Сумма implementation units:
- Hours per unit:
- Базовые часы:
- Discovery:
- Миграция или обработка данных:
- Production-like bulk/external coordination/special hardware:
- Необычная длительная или ручная проверка:
- Другие исключительные конкретные работы:
- Итоговый диапазон:

Обычные focused tests, static checks, XML compilation, один module update и
обычный smoke уже входят в cluster. Не добавлять их повторно. Дополнительные
часы указывать только для конкретной работы вне нормальной поставки. Risk flags
объясняют неопределённость, но сами по себе не добавляют часы.

Эмпирические ориентиры итогового времени:

| Размер | Типичный scope | Время мидла |
|---|---|---:|
| trivial | Один известный XML-атрибут, label, domain, filter или insertion | 0.25–0.75 ч |
| small | Одно связное model/view extension по известному паттерну | 0.75–2 ч |
| normal | Несколько связанных hooks внутри одного addon/subsystem | 2–5 ч |
| medium | Нетривиальный lifecycle или несколько взаимодействующих подсистем | 5–12 ч |
| large | Stock/MRP/Accounting, migration, concurrency или external integration с существенным риском | 1–3 дня или больше |

Fast path применяется, если scope содержит не более одного связного model
extension и двух простых view-изменений и не содержит migration, новой security
model, cross-subsystem lifecycle, Stock/MRP/Accounting side effects, concurrency
или external integration. Для него давать компактный эмпирический диапазон,
обычно 0.75–2 часа; units использовать только для проверки здравого смысла.

### Module update и smoke verification

- 

Для простых декларативных XML/view-изменений обычно достаточно:

- успешного обновления модуля;
- компиляции наследованных view;
- проверки XPath/XML references;
- focused smoke verification затронутого UI.

Dedicated automated tests нужны, когда изменение содержит нетривиальный domain,
security behavior, computed search, lifecycle logic или защищает известную регрессию.
