## Покрытие сценариев

| Спецификация | Scenario | Классификация | Cluster | Risk flags | Обоснование |
|---|---|---|---|---|---|
| | | implementation-driving / verification-only | | | |

Классификация:

- `implementation-driving` — требует нового или изменённого production-поведения;
- `verification-only` — не требует отдельной реализации и проверяет общий
  механизм, стандартное поведение или отсутствие регрессии.

Каждый Scenario должен присутствовать в таблице ровно один раз.

## Implementation clusters

| Cluster | Механизм реализации | Покрываемые сценарии | Units | Обоснование |
|---|---|---|---:|---|
| | | | | |

Использовать только значения:

| Units | Значение |
|---:|---|
| 0 | Только проверка; независимое production-изменение отсутствует |
| 0.25 | Очень маленькое декларативное изменение: простой filter, domain, label, attribute или известная XML-вставка |
| 0.5 | Небольшое изменение одного view/configuration record либо повтор уже установленного паттерна |
| 1 | Законченное локальное изменение одной модели, view или известного extension point |
| 2 | Согласованное поведение связанных записей внутри одной подсистемы |
| 3 | Нетривиальная кастомная логика или стандартный handoff между подсистемами с focused validation |
| 5 | Существенная lifecycle-координация, cancellation/retry или несколько взаимодействующих записей |
| 8 | Сложная логика Stock, Procurement, MRP, Accounting, миграции, bulk, external integration или failure recovery |
| 13 | Крупная неделимая архитектурная неопределённость; требуется split или discovery |

Правила:

- Оценивать общий механизм реализации, а не каждый Scenario отдельно.
- Не считать один и тот же code/XML/configuration mechanism несколько раз.
- Для повторов одного паттерна учитывать только добавочную стоимость.
- Standard Odoo, существующий проектный код и legacy должны уменьшать Units,
  если реально сокращают реализацию.
- Не считать отдельными clusters изменение версии модуля, manifest, файлы,
  тесты или описание регрессии.
- Не применять дополнительный коэффициент за количество addons, моделей,
  файлов или затронутых доменов.

### Module update и smoke verification

- 

Для простых декларативных XML/view-изменений обычно достаточно:

- успешного обновления модуля;
- компиляции наследованных view;
- проверки XPath/XML references;
- focused smoke verification затронутого UI.

Dedicated automated tests нужны, когда изменение содержит нетривиальный domain,
security behavior, computed search, lifecycle logic или защищает известную регрессию.
